# 041 - Instance Lock 与 WAL Path 同步

- **类型**: bugfix
- **严重级别**: P1-HIGH
- **日期**: 2026-04-15
- **Commit**: `64045a4` (merge), branch commit: `ea39ad7`

## 问题描述

两个独立问题：

**R3-1**: 多个应用实例同时运行时，共享的 WAL/索引文件会发生数据损坏，缺乏进程级互斥保护。

**R3-2**: `compact()` 通过 rename 将 `.wal.new` 替换为标准 WAL 文件后，内部 `path_` 成员未同步更新，仍指向旧的 `.new` 路径。下一次 compact 周期中 `closeAndDelete()` 删除的是已过时的 `.new` 路径，导致当前活跃 WAL 文件被误删。

## 根因分析

**R3-1**: 应用层缺乏实例互斥机制。macOS 允许多次启动同一应用，多个进程并发读写同一组持久化文件会导致数据竞争和文件损坏。

**R3-2**: rename 操作只更新了文件系统中的文件名，但 WAL 对象的 `path_` 成员未随之更新。后续操作基于过时路径执行删除，目标文件已不存在或指向错误文件。

## 修复/实现方案

**R3-1**: 实现 `InstanceLock` (RAII flock) 机制，在 `MacSearchBridge` 初始化索引前获取文件锁，确保同一时刻只有一个应用实例访问持久化文件。

**R3-2**: 在 `compact()` 完成 rename 后立即调用 `updatePath()`，使内部 `path_` 与文件系统中的实际路径保持同步。

## 影响的文件

- `MacEverything/Core/InstanceLock.h` — RAII flock 锁定义
- `MacEverything/Core/InstanceLock.cpp` — 锁获取/释放实现
- `MacEverything/Bridge/MacSearchBridge.mm` — 启动流程集成 InstanceLock
- `MacEverything/Core/IndexWAL.cpp` — compact() 后调用 updatePath()

## 测试覆盖

- InstanceLock 互斥行为测试
- WAL path 同步后连续 compact 不再出现 ENOENT 错误的验证
