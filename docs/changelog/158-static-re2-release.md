# 静态 RE2 依赖与启动校验

**日期**：2026-10-20

## 根因与 fork 评估

错误日志的关键不是找不到文件，而是 dyld 已经找到 Frameworks 中的 RE2，却因主程序和库的 Team ID 不匹配而拒绝加载。ad-hoc 签名不提供 Team ID；把应用和每个 dylib 都用 `-` 重签，并不等于它们拥有同一个开发者身份。`codesign --verify --deep --strict` 验证通过，也不能证明这些库能被 Hardened Runtime 加载。

对比 szh0721/MacEverything 的提交 `721d7105e19b97e541677a33dcd782910d08d403`：

- 对签名根因的判断合理。证书签名场景中，让嵌入代码使用 Xcode 展开的同一个证书身份，值得参考。
- 为 ad-hoc 发布关闭 Hardened Runtime，是其主要兼容性处理，但会改变应用的运行时保护策略。本项目不采用这个方案，也不增加关闭库验证的 entitlement。
- 增加真实 Mach-O 签名测试的方向值得参考；只做签名完整性检查不足以覆盖启动错误。
- fork 基于较早的共同祖先，不能直接覆盖本项目后续卷生命周期和增量签名修复；这里只参考相关诊断和测试思路。

## 修复

- 从 SHA-256 固定的 RE2 `2025-11-05` 和 Abseil `20260107.1` 官方源码编译静态库，将依赖合并为 `libre2_bundle.a`。
- Xcode 和命令行测试统一静态链接；不再修改 Mach-O 加载命令或重签第三方动态库。增量构建清理旧版本残留的 RE2/Abseil dylib。
- 保留 Hardened Runtime 和库验证，应用只允许依赖系统动态库。
- 发布检查验证签名完整性、运行时保护、架构、动态依赖和个人构建路径；依赖编译使用文件路径映射，避免 Abseil 日志字符串包含开发者主目录。
- `test_all` 和 benchmark 显式依赖 Makefile 和静态库，避免链接参数改变后继续运行旧的动态链接二进制。
- 通过 macOS Foundation 网络栈下载源码，沿用系统代理配置。源码、中间产物和相关仓库工作副本保留在 `build/`，`artifacts/` 仅包含最终应用和安装包。
- 应用资源附带 RE2 和 Abseil 许可证。

## 自动化验证

- `make test-fast`：串行核心快速测试 1924 项通过，Swift/Bridge/本地化/文档检查通过。
- `make test-release-signing`：7 项真实 Mach-O 回归测试，覆盖迁移后静态 RE2 应用启动、旧动态依赖拒绝、Hardened Runtime 缺失、资源篡改、架构不符、增量构建残留清理和 MCP Bundle 版本读取。
- Intel 静态依赖和应用在 Apple Silicon 上交叉编译；签名/加载测试通过 Rosetta 运行。
- 双架构 Release 构建和 DMG 挂载安装副本检查；真实应用在隔离用户目录中运行 8 秒未退出，包内 CLI 帮助和 MCP 协议各 45 项测试通过。异机安装与完整 GUI 验收仍由用户执行。
