# 卷生命周期与监听时序修复

**日期**：2026-10-18

## 修复内容

- `/Volumes` 路径不再一律当成已拔出的外置盘。只有以前挂载时确认过的本地外置盘，在现在不可达时才会推迟扫描并清理其缓存记录。
- 指向已挂载文件系统的符号链接（例如 `/Volumes/Macintosh HD`）、`/Volumes` 下的普通目录、离线的 SMB/NFS，以及尚未分类的路径，都会保留已有索引。
- 挂载表改用线程安全的 `getmntinfo_r_np()`。失败时返回 0，调用方会把它当成查询失败而不是“没有挂载”，因此不会据此删除缓存或放行重建。
- 重建索引时，离线网络卷或未知根目录会阻止删除旧索引文件。
- 卷挂载或卸载通知若发生在全量扫描或后台同步期间，会延后到该阶段结束再启动 FSEvents，并补做当时排队的子树重扫，避免实时事件被随后的 `loadRecords` 覆盖。
- 构建只使用 ad-hoc 签名和同一份 entitlements。嵌入的动态库与应用使用同一签名身份，强化运行时可以加载 libre2。`make app` 会用 `codesign --verify --deep --strict` 检查签名。
- 卷分类同时保存卷 UUID，以及缓存记录所属的 UUID。挂载名相同但身份对不上、或还没有索引身份时，不会清理缓存。
- 切换缓存目录会清空内存中的卷分类，再从新文件加载。每个 `ServiceEngine` 使用自己的分类存储，后创建的实例不会把分类写进另一个缓存目录。
- 损坏的 `volume-kinds.tsv` 若带有溢出的字段长度，会跳过该行，而不是在启动时抛出异常。
- 延迟的子树重扫在真正改索引之前会再次检查生命周期；扫描或重建已经开始时重新排队，并使用当前发布的引擎。
- 卷卸载删除同样会在修改索引前检查生命周期。扫描或重建期间到来的删除会延后，并作用在当前发布的引擎上。
- 子树重扫若覆盖了某个卷上的全部配置根，会记下这些缓存记录所属的卷 UUID。只扫到其中一部分时不更新，避免把同名卷上尚未替换的旧记录标成新盘。
- 全量扫描成功后会先标记启动完成，再执行扫描期间排队的挂载重扫。直接调用全量扫描的路径也会走这同一顺序。卷 UUID 要等这次扫描结果发布成当前索引之后才写入。
- 拖拽重命名若发生在扫描或同步期间，会延后到当前引擎发布后再应用，不会写进即将被替换的旧引擎。
- 子树重扫、实时 FSEvents 和启动时的事件重放，都会在同一把生命周期锁里完成代次检查、读取当前引擎和写入索引。扫描或重建已经发布新引擎时，这些修改会重新排队，而不是写进即将被换掉的引擎。
- 全量扫描和增量启动会在那把锁里置上扫描状态，重命名不会赶在状态生效前写进旧索引。
- 后台全量替换在 `loadRecords` 期间持有同一把锁。这次扫描会丢掉尚未应用的重放批次，用户排队的重命名、删除和重扫仍会在发布后执行。
- 延迟的文件系统事件带上产生时的生命周期代次。代次已经变化时直接丢弃；重建索引在替换引擎后也会清掉这些批次，避免过期的删除写进新扫描结果。
- 后台全量替换在 `loadRecords` 前推进索引快照编号，生命周期代次保持不变。已经从延迟队列取出的旧事件仍带着旧编号，不会写进新扫描出的记录。全量扫描发布新引擎时同样推进这个编号，并只丢掉文件系统事件。用户排队的重命名、删除和重扫不看这个编号。扫描期间的真实变更从扫描起点重放。
- 卷通知若在扫描已经开始后才启动监听，会在监听锁里看到扫描状态并推迟。扫描结束时若已经有一条从“现在”开始的流，会改从扫描起点重新监听，避免跳过扫描期间的重放。
- 后台重放成功后，实时监听从重放流交付过的最后事件编号接上；重放没有记到编号时，沿用启动重放时的水位。后台全量扫描在开扫前记下事件编号，发布后从该编号重放扫描期间的变更。全量扫描不再在监听锁外改写 watcher 水位。
- 同一次排空的延迟操作在变更队列上按到达顺序执行。
- 嵌入运行库时，只有加载命令确实变化才重签内部映像。内部签名或 app 密封失效时，用本次构建的身份、entitlements 和强化运行时重新签整个 app，增量 `make app` 可以通过严格签名校验。
- 延后的卸载删除在执行前会再看路径是否已经重新挂上。已经挂上的同名路径不会被这条旧删除清掉。
- 首次全量扫描失败时，排队的卷操作仍会执行并调用完成回调，不会一直等到下一次成功启动。
- 监控启动、停止和网络轮询计时器共用一把锁，避免同步结束和挂载通知同时各启动一套 watcher。
- 候选复用测试改为在删除之后先重建缓存，再检查压缩是否使缓存失效。
