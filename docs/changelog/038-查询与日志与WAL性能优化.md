# 038 - 查询/日志/WAL 性能优化

- **类型**: performance
- **日期**: 2026-04-15
- **Commits**: `d70d63f` (merge), `8979865` (merge), `f50a35c` (merge)

## 问题描述

三处独立的性能瓶颈：

1. **查询**: trigram 候选项过滤使用 `binary_search` 的 O(log N) 复杂度，在大量记录下成为热点
2. **日志**: 每次写入都执行 flush 和初始化检查，高频日志场景下开销显著
3. **WAL**: 每次写入通过 `fstat` 系统调用获取文件大小，产生不必要的用户态/内核态上下文切换

## 修复/实现方案

**查询优化**:
- 将 trigram 候选项的 `binary_search` (O(log N)) 替换为 `vector<bool>` 位集 (O(1)) 查找
- 在构造 `lowerPath` 之前先检查 `lowerNames`，避免不必要的路径转换开销

**日志优化**:
- 实现批量刷新策略：每 32 次写入执行一次 flush（ERROR 级别仍立即刷新）
- 将 `initialized_` 检查前置，快速跳过未初始化状态
- 修复 `LOG_TIMER` 宏中 `__LINE__` 展开问题，确保唯一变量名

**WAL 优化**:
- 用内存中的 `currentSize_` 计数器替代 `fstat` 系统调用
- 消除每次写入时的用户态到内核态上下文切换

- 验证批量 flush 在正常退出时不丢失日志

- LOG_TIMER 宏在同一函数多次使用时编译通过
