## 3. 问题分析

### 整体诊断

R17 是 **flush 后预热轮次**（距第 2 次 flush ~6min），整体性能大幅恢复：
- avg 44.1ms（R16 冷启动 86.6ms，**-49%**）
- 接近 R15 热缓存水平（34.7ms，仅差 +27%）
- GCD 路径完全恢复：`test type:folder` 61ms、`test path:/usr` 55ms（均优于 R15）
- Regex-trigram 大幅恢复：avg 49.7ms（R16 100.1ms，-50%）

**但 `a` 异常偏高 234.9ms（17 轮最差之一）**，以及 `content:batchMutate` 181ms 仍偏高。

### 现有问题更新

| 问题 | 状态 | R17 表现 | 备注 |
|------|------|---------|------|
| P0 trigram 阈值 | Critical | `test` API 45ms / 日志首查 424ms | **日志首查仍 424ms，强化论据** |
| P1 GCD filter | Medium | 55-61ms | 恢复至 R15 水平 |
| P2 regex 候选集 | Medium | 67ms（48788 候选） | 恢复 |
| P3 content 搜索 | Medium | **181ms** | 偏高（R15 105ms，+73%） |
| P7 锁争用 | Medium | lock_wait=0ms | 本轮无复现 |
| P12 structured 冷启动 | Medium | 44.7ms | 恢复 |
| P16 flush 组合劣化 | Medium | 日志首查 424ms | flush 后 VM 重缓存 |
| P17 glob-trigram 冷启动 | Medium | 5.4ms（部分恢复） | 预热后趋于消除 |

### 新发现

**`a` 234.9ms 异常**：R17 `a` 查询是本轮最慢的 benchmark 查询，且比 R16 的 156ms 还高（+51%）。日志确认 `a` 延迟 234ms = API 234.9ms，匹配。可能原因：
- `a` 在 benchmark 第 1 个位置执行，是当轮首个 linear scan 查询
- 本轮 `results=5`（limit=5），需遍历 5.27M 条记录找到 5 个以 `a` 开头的文件
- scan=228ms + sort=6ms，scan 阶段花费 228ms 是 VM 页面未完全预热的表现
- 后续 linear 查询（`ab` 48ms、`test` 45ms）显著快于 `a`，说明 `a` 为当轮 linear 路径做了预热

**GUI 查询 `ex` 460ms**：用户实际使用场景中 2 字符查询延迟感知明显。进一步强化 P0 需求。

## 4. 优化建议

维持 6 条优化建议，R17 数据更新论据：

1. **放宽 trigram 降级阈值**（P0）— `test` 日志首查仍 424ms，GUI `ex` 460ms，走 trigram 可降至 <10ms
2. **Regex 查询提前终止**（P2）— 67ms，候选 48788
3. **内容搜索直接查内容索引**（P3）— 181ms，flush 后偏高
4. **date filter 支持**（P4）— 仍走 linear，0 结果
5. **多词查询独立 trigram + 交集**（P5）— `search engine query` 40ms 走 linear
6. **Flush/启动后预热**（P16/P17）— 消除首查 424ms 峰值

## 5. 总结

R17 是 flush 后预热轮次（WAL 5,489 条，2 次 flush 后 ~6min），性能大幅恢复：
- avg 44.1ms（R16 86.6ms，**-49%**），接近 R15 最佳水平（34.7ms）
- GCD 路径恢复至最优：`test type:folder` 61ms（**优于 R15 的 80ms**）
- Regex-trigram 恢复：avg 49.7ms（R16 100.1ms，-50%）
- P17 glob-trigram 恢复至 5.4ms（R16 115.8ms）
- lock_wait=0ms，无崩溃，无错误
- **`a` 234.9ms 异常偏高**（R16 156ms，+51%），为 linear 路径首查 VM 预热开销
- **GUI `ex` 460ms**：实际用户查询场景，P0 优化的直接受益点
- **`test` 日志首查 424ms**：持续强化 P0 trigram 阈值优化论据
- **WAL 持续增长**：316→3,319→5,489，会话间文件变更活跃
